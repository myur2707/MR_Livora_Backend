# Step 10: notices and complaints

Committee Admin and Committee Member require explicit `society.notices.manage` / `society.complaints.manage` grants. Resident, accountant and platform roles have no implicit management access. Every request revalidates live session context, active society/membership, effective tenant person and permission/role ceiling in a transaction. Assignees must be active committee members of the same society with complaint management permission.

## Notices

`/api/v1/society/community/notices` provides paginated status/search lists and create/detail operations. POST `/:id/edit` edits draft or published text; POST `/:id/action` publishes a draft or archives a draft/publication. Archived notices are terminal. New drafts are hidden from residents; publishing records server UTC time and the authenticated author membership. An edit preserves the original author and publication time; `notice_details` records last editor/time/revision. Every mutation is audited without placing notice text in security logs. Publication is society-wide, with no external notification or read-tracking integration.

## Complaints

Residents submit category/title/description for a currently authorized flat. Categories: MAINTENANCE, PLUMBING, ELECTRICAL, SECURITY, COMMON_AREA, OTHER. Missing category from an older client defaults to OTHER. Only the submitting membership can read its resident complaint/detail/history, including after occupancy ends while membership remains active. Committee endpoints `/api/v1/society/community/complaints` provide paginated status/category filtering, details, history, eligible assignees and POST `/:id/status`.

The server enforces `NEW → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED`. Assignment is required before work starts. ASSIGNED/IN_PROGRESS permit reassignment with a different eligible assignee and a resident-visible note; no reopening or status skipping is supported. Resolution timestamps are server-derived. Updates require expected revision and a note. Society/record locks plus revision conflicts prevent lost updates; workflow, append-only history and audit commit together. History and assignee lists paginate independently. History notes are visible to the submitter; there is no confidential internal-note field.

## Additive migration and compatibility

Migration 014 adds `notice_details`, `complaint_workflows` and `complaint_status_history`, tenant-composite foreign keys/indexes/checks and immutable-history/delete guards. Applied migrations 001–013 remain unchanged; no existing rows are backfilled or overwritten. The old complaints table's status constraint cannot express NEW/ASSIGNED. `complaint_workflows.status` is authoritative when present; otherwise old OPEN maps to NEW and other old statuses pass through. All new queries use this shared projection, never the legacy status directly. Legacy category is OTHER; legacy unknown resolution time remains unknown. First committee mutation creates the workflow at the next revision; preceding history is not invented. Existing complaints/title/description/author rows stay intact. History actors/assignee relationships remain tenant-scoped and are not included in resident history DTOs.

Run migrations with the separate migration identity, then provision permissions with `npm run db:community-permissions` and table-specific runtime grants from `src/database/community-grants.ts`. Provisioning adds the two new permissions only to canonical active committee roles already granted dashboard access; existing restrictions on unrelated permissions remain. Runtime has no DELETE grant on community records and no UPDATE/DELETE grant on history. Managed `local:stop` / `local:start` applies the additive upgrade and grants while preserving credentials/data. Rollback means disable the new routes and retain tables/history; do not drop production data.

## Text and security model

Assets are tenant drafts, published updates, complaint descriptions and immutable status history. Actors are residents, authorized committee, and unprivileged other tenants/platform administrators. Trust boundaries are browser → authenticated/CSRF-protected API → least-privilege MySQL. Strict schemas reject protected fields, invalid identifiers/categories, oversized text and control characters; plain multiline text is trimmed. HTML-like content is stored literally and rendered only through Angular text interpolation, never innerHTML or sanitizer bypasses. Attachments are not supported. API responses are no-store and the PWA caches static assets only. Audit metadata excludes complaint/notice body and notes. UTC timestamps are displayed in the browser's local time on committee screens; tenant business dates remain society-local dates.

Published notices intentionally attribute their author by tenant display name. This is part of the society-wide publication, not directory access; author contact information/global account IDs are never returned in resident notices. Drafts and author membership identifiers stay committee-only. Complaint history exposes status, note and UTC timestamp to its submitter; staff actor/assignee identifiers are excluded from resident DTOs. The society lock serializes complaint updates without granting UPDATE on legacy complaints; notice rows are also locked during mutation.

Tests cover publication visibility, terminal archive, stale/concurrent revisions, complete complaint transitions, invalid and cross-tenant assignees, mass assignment, role ceilings, CSRF, resident ownership, legacy compatibility, tenant foreign keys and immutable history. Browser tests exercise associated validation, safe literal rendering, publishing/archive and complaint assignment/resolution.
