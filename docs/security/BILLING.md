# Step 7 billing threat model

Assets are charge policy, immutable bills/adjustments, private flat financial balances, membership permissions, session/CSRF tokens and audit history. Actors are committee administrators, accountants, residents, platform operators and unauthenticated clients. Browser, API, runtime DB account and migration/operator DB account are separate trust boundaries. Browser guards and computed displays grant no backend authority.

Cross-tenant identifiers, mass assignment, forged totals/discounts, role revocation races, repeated generation, stale previews, one-time-event reuse, floating-point rounding and unauthorized ledger edits are material abuse cases. Strict allowlisted schemas, session/membership/role ceiling checks inside locked transactions, composite FKs, exact BigInt/DECIMAL money, bounded batches, canonical preview hashes, idempotency, immutable snapshots and database uniqueness/guards mitigate them. Platform roles never imply tenant finance access. Discount reasons and actors live in restricted immutable adjustments; audit records only necessary action/run/kind metadata. Ordinary logs contain correlation IDs and safe error codes, not money, tokens or resident details.

All POSTs require same-origin JSON and CSRF. General API and generation-specific limits mitigate abuse. APIs always send no-store, and the PWA caches hashed application code/static shells only. Financial data is held in component memory and cleared on loading failure; it is not stored in localStorage, IndexedDB or service-worker response caches. Production uses the existing HTTPS secure session cookie policy. No CSV exports, payment collection, interest or payment credentials are introduced.

The society lock favors correctness over parallel generation throughput; the 50-flat limit bounds lock duration. Lock order matches existing user/session → society → membership checks. Database errors/deadlocks become safe conflicts, never success. Configuration changes require a new version. The dedicated migrator/operator is trusted and must protect backups/audit retention; the runtime account has restricted column/table grants. Append-only records have no automatic deletion retention job. A reviewed retention/reversal workflow is needed before any later archival of financial history.
