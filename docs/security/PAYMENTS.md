# Payment recording threat model

Assets: private financial history, receipt integrity, collector/recorder attribution, bill debt, immutable reasons/audits and resident display names. Actors: authorized committee admins/accountants, restricted residents/members, Platform Admin, stolen-session holders and malicious concurrent callers. Boundaries: browser→cookie/CSRF authenticated API→session-derived active tenant→transactional least-privilege MySQL; print output is private and controlled by the user. No gateway or bank trust boundary is introduced.

| Abuse                                                              | Mitigation and tests                                                                                                                                                                                |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Change society/payment/bill/flat/person/collector or recorder      | Strict schemas reject society/recorder/membership fields; live active membership/permission/role ceilings; tenant/flat composite FKs; tenant lookup/receipt tests; recorder derived from session    |
| Resident/Platform Admin reads finance or accountant returns money  | Finance read/record/reverse capabilities and separate committee-only reversal ceiling; platform has no implicit finance; HTTP permission tests                                                      |
| Disabled/foreign/unprivileged collector                            | Validate active user/membership/person/role permission under locks on every recording; choices expose no contacts; negative collector tests                                                         |
| Cross-site state change or stolen old context                      | HttpOnly/SameSite session, origin-bound CSRF, session expiry and context recheck within transaction; shared Step 3 tests plus payment CSRF test                                                     |
| Concurrent overpayment, duplicate request or reference             | Exact BigInt sums, bound amounts, society/bill locks, immutable tenant request keys/hash, noncash reference duplicate check under society lock; concurrent distinct-session and identical-key tests |
| Oversized/malformed money/date/filter/allocations or SQL injection | Validated strict boundary, max 50 allocations/page, positive DECIMAL(12,2), allowlisted query fields and parameterized values; API/unit tests                                                       |
| Refund more than original allocation or reverse twice              | Header/original allocation ceilings, immutable refund ledger, unique full reversal, DB guards, separate no-refund-plus-reversal policy; return/reuse/race tests                                     |
| Crash between payment, allocation, receipt, correction or audit    | One transaction with completion seal, injected writer failure/rollback tests; original correction reversal also rolls back                                                                          |
| Rewrite history, renumber receipt, delete parent                   | Append-only baseline/new triggers, SELECT/INSERT-only finance grants, restrictive FKs, ID-based unique numbers/snapshots and history tests                                                          |
| Private financial browser cache/log leakage or script injection    | API no-store; memory only; Angular escaping; static-only worker/private bypass/offline checks; no raw requests/notes/references/tokens in ordinary logs; audit stores IDs and action metadata only  |

Record limits supplement shared IP/session rate limits. Foreign/missing resources share safe 404 responses; validation/conflicts expose no SQL, stack or global identity details. GET receipt requires current finance authorization rather than possession of receipt/payment number. Print mode includes status and refund/reversal history, hides app navigation, and creates no server-side/public file. OS print/PDF output must be treated as the user's private financial document.

All-time report reconciliation is covered against retained source payments/reversals/refunds. Separate permission and immutable reasons make corrections reviewable, but software cannot verify that physical cash was received/returned; committee reconciliation is required. Archived people/collectors preserve receipt snapshots. Financial/audit retention follows the baseline legal/operational retention policy; no automated purge is added. Legacy unallocated records are explicit reconciliation exceptions, not auto-repaired.
