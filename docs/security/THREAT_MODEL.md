# Step 3 threat model

Assets: account passwords, session/reset tokens, society membership grants, tenant private/financial data, immutable security audit. Actors: anonymous visitors, residents, committee members, accountants, platform operators, attackers with another tenant account, and deployment/DB operators. Trust boundaries: browser to same-origin HTTPS API, API to restricted MySQL, API to authenticated TLS SMTP, and privileged provisioning to runtime.

| Abuse case                        | Mitigation/test                                                                                                                                                             |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Credential theft/database leak    | Argon2id 19 MiB/2 passes/1 lane with random salt; opaque tokens hashed at rest; no secret logs/bundles                                                                      |
| Session fixation/replay           | Fresh token/CSRF after login; old session revoked; database idle/absolute expiry and logout/reset revocation                                                                |
| CSRF/login CSRF                   | Exact Origin, synchronizer HMAC token even for anonymous writes, JSON-only, SameSite=Lax, cross-site fetch rejection                                                        |
| User/role/tenant forgery and BOLA | Strict schemas; identity from opaque cookie; live membership joins; scoped resource SQL and composite FKs; negative HTTP probes                                             |
| Platform overreach                | Platform assignments separate from tenant role grants; no tenant bypass; runtime cannot read finance                                                                        |
| Account enumeration               | Same login status/message with dummy Argon2 work for missing/passwordless account; deferred reset lookup/SMTP and identical 202; known/unknown have identical limiter logic |
| Brute force/reset spam            | Shared transactional fixed-window account/IP/token limits; bounded mail jobs, 16 KiB bodies, request/header timeouts                                                        |
| Reset replay/races                | 256-bit hash-only token, expiry, prior-token invalidation, account-first locking, transactional single-use + session revocation                                             |
| SQL/mass assignment               | Fixed parameterized SQL and allowlisted body fields; separate restricted runtime/migration accounts                                                                         |
| Private PWA/cache leakage         | API no-store; Angular worker caches only hash-versioned static files, no data groups; tokens remain memory-only and reset fragment is cleared                               |
| Internal error/log disclosure     | Central reviewed codes/correlation IDs; production 500 tested with synthetic SQL/path/stack failure; logs omit raw exceptions                                               |
| Audit tampering                   | Append-only triggers, no runtime SELECT/UPDATE/DELETE on auth_events, restrictive user FK                                                                                   |

Residuals: XSS can act as the signed-in user even though HttpOnly blocks reading session cookies; preserve safe Angular interpolation, static-only CSP-compatible assets and a restrictive deployment CSP. A stolen active cookie remains usable until expiry/revocation; Step 3 has no MFA/device management. Distributed bot traffic requires deployment edge controls. Reset mail depends on configured SMTP; the bounded in-process queue is not durable. Fixed-window boundaries permit bursts. Membership middleware reads current state but future business writes must revalidate within their transaction. Database and SMTP administrators remain trusted operators; no app-layer design protects against a fully compromised host.

Password parameters follow [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Newly set passwords require 15–128 characters without composition rules; the minimum follows [OWASP authentication guidance for accounts without MFA](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). Cookie/CSRF policy follows [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html); SMTP requires [Nodemailer TLS transport](https://nodemailer.com/smtp).
