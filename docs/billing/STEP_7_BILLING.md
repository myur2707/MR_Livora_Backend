# Maintenance configuration and bill generation

Step 7 exposes `/api/v1/society/billing`. Authentication, active society selection, active membership, role capability ceilings and database permissions are rechecked inside every transaction. Platform status gives no financial access. Committee Admin can configure, generate and authorize discounts; Accountant can read/generate but cannot configure or discount. Residents and Committee Members have no Step 7 financial routes. These permissions are separate from future payment recording.

## Approved policies

- Monthly billing covers a calendar month. Charge eligibility and configuration are evaluated on its first day. The user approved the full monthly amount with no proration. Mid-month changes apply at the next monthly anchor. Occupancy end dates are inclusive, consistent with Step 5.
- Each charge type has an immutable MONTHLY or ONE_TIME frequency. A one-time period covers one day; each one-time type is an event, consumed once for each flat across all periods/configuration versions. Create a distinct charge type for a new event. A monthly bill and a one-time bill can coexist, using separate periods; issued bills cannot be extended.
- For each charge type, flat overrides building, which overrides society. Each target uses its most recent effective start date not after the billing anchor, then highest version for that date. A disabled or expired override excludes that charge; it never revives an older version or falls back to a broader target. ALL_FLATS includes active vacant flats; OCCUPIED_ONLY needs any occupancy covering the anchor. No login is required for the occupant. Archived buildings/flats and archived charge types cannot receive new charges.
- New configuration versions are appended. Existing onboarding configurations default to MONTHLY, society/flat scope, enabled and ALL_FLATS without rewriting data. Existing periods default to MONTHLY. Legacy bill descriptions and amounts remain readable; a missing historical snapshot is explicitly marked rather than invented.
- **Previous outstanding is informational only.** It sums other issued bills' remaining balances for the flat. It is snapshotted separately and never becomes a new bill item or an additional collectible debt. There is no interest, late fee or arrears capitalization in this step.
- Discounts require `society.finance.discount`, a positive fixed amount or percentage at most 100, and a reason of 5–500 characters. They are issued as immutable CREDIT adjustments during generation. `bills.total_amount` remains the gross sum of items; net = gross + debit adjustments − credit adjustments. This prevents subtracting a discount twice. Retrospective discounts/edits are outside Step 7.

## Money and status

All authoritative amounts/rates are decimal strings backed by DECIMAL(12,2). TypeScript converts to BigInt minor units. Quantity uses hundredths of a square foot or `1.00` for fixed rates. Each positive line is rounded half up to two decimals before summing. Percentage discount is rounded half up once against that summed gross. No authoritative calculation uses JS floating point. Input with more than two decimals is rejected. Overflow, negative values, zero-value discounts and discounts above gross are rejected; line/bill/preview totals cannot exceed `9999999999.99`. Database item checks independently require `ROUND(quantity * unit_rate, 2)` to match. [MySQL exact decimal rounding](https://dev.mysql.com/doc/refman/8.4/en/precision-math-rounding.html) agrees with the positive half-up policy.

Persistent bill status stays DRAFT/ISSUED from Step 1. Generation issues immediately inside one transaction; draft financial records are never exposed by generation. Settlement is derived: DRAFT, SETTLED, OVERDUE, PARTIALLY_PAID or UNPAID. Outstanding = max(net − non-reversed allocations, 0); over-allocation is separately shown as credit balance. Reversed payments do not settle bills. Reports paginate and use exact SQL DECIMAL sums. Society timezone determines the current local date/due-date display; stored event timestamps use UTC. No payment/receipt write APIs are included.

## Requests and concurrency

GET `charge-types`, `configurations`, `periods`, `buildings`, `flats`, `bills`, `outstanding` accepts bounded page/pageSize, q and validated optional buildingId/periodId/status. Results have stable descending ID order; arbitrary SQL sort fields are rejected. GET `bills/:id` returns snapshot items and adjustments. POST `charge-types`, `configurations`, `periods` is configuration-only. POST `preview` takes periodId, 1–50 unique flatIds and optional per-flat discounts. POST `generate` adds previewHash and a 16–80-character idempotencyKey. Client society/actor/totals/protected fields are rejected. Lookup endpoints intentionally provide billing metadata without requiring resident-management access.

The server recomputes the canonical preview inside a transaction under the society lock. A changed preview returns `409 PREVIEW_CHANGED` and requires review. Same key and identical canonical body return the original committed bill IDs; different body returns `409 IDEMPOTENCY_CONFLICT`. Tenant/flat/period uniqueness and one-time consumption uniqueness supplement the lock. Concurrent different keys cannot double issue. No finalized bill is replaced. At most 100 lines per bill and 5,000 applicable configurations per selected batch are accepted. The UI retains selections across paginated flat lookups, requires explicit issue confirmation and keeps the same in-memory key/body after an uncertain network result. A refresh requires reviewing the current bill list and a fresh preview.

Items, gross totals, discounts, one-time consumption, snapshots, generation completion and audit are atomic. Failure rolls everything back. Immutable snapshots preserve period dates, building/flat labels, item descriptions/rates/quantities and prior outstanding. Completed run identity, hashes and audit cannot be changed/deleted. Existing completed financial triggers and restrictive foreign keys remain intact. Runtime grants exclude financial DELETE, configuration UPDATE, audit UPDATE/DELETE and payment writes.

## Migration and local operation

Migration `012_billing.sql` adds seven metadata/history tables and twenty triggers (27 additive statements). It does not alter, erase or backfill existing rows. MySQL DDL is not transactionally reversible: inspect STARTED migration failures manually, never automatically retry/clean up. Reverting application deployment does not require removing financial data. Financial metadata/configuration/periods are immutable; append corrections and retain history. Parent deletion is restricted.

Run `npm run db:migrate`, then `npm run db:billing-permissions` using the dedicated migrator, and provision the restricted grants from `src/database/billing-grants.ts` using an authorized database operator. Permission provisioning is idempotent/additive and grants new capabilities only to canonical roles already holding both finance.read and finance.record; existing deliberately restricted roles retain their restrictions. New onboarding societies obtain the same role capability mapping. Runtime never performs DDL or startup permission provisioning.

For the owned Windows manual environment, `npm run local:stop` then `npm run local:start` rebuilds both projects and safely applies pending additive migrations/grants while preserving accounts and data. Open `http://127.0.0.1:4200`, sign in as Committee Admin, select an ACTIVE society, then use Charge configuration → Billing periods → Generate bills → Bills / Outstanding. Never rerun account setup to upgrade an existing environment. New disposable integration schemas are prefixed `livora_test_`; tests refuse nonempty/shared schemas. Development test passwords are synthetic and are never production seeds.

## Manual verification

Create a monthly type, society configuration, optional building/flat override and full calendar period. Select occupied and vacant flats, preview and confirm. Compare detail lines, gross, discount, net and report balances. Change a future version and confirm issued amounts do not change. Retry the same generation; IDs stay the same. Try a different key against the same billable flats; it cannot overwrite the bill. Verify Accountants cannot discount/configure and residents/platform-only accounts cannot read bills. Try a foreign society's period/flat/bill ID, invalid dates, extra actor/society fields and missing CSRF. Verify one-time events cannot be billed again through another period/version. Network/offline pages must show an error rather than cached financial data.
